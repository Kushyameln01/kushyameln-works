# Animator Composer 改良計画

版 1.0（提案・静的レビュー済み） / 2026-10-18 / 計画の段階

**既存の構造統合・比較・出力を保全し、任意診断が加える読込み・表示・コピーの負担を減らす。最初に現行版の比較基準と計測条件を固定し、初期読込みと診断表示の改良から進める。**

今回の成果は改良計画である。製品コードの変更、製品の再実行、Sites/GitHub Pagesの更新は行っていない。以下の実装方法・計測回数は提案であり、新たな確定仕様として扱わない。

## 2. 維持する製品の目的と条件

利用者が既存Controller等を読み込み、統合対象と参照・Parameterの扱いを判断し、同じ構成から同じ意味の出力を得られる状態を維持する。共有診断は、その判断とChatGPTによる把握を補助する。

| ID | 継承する条件 | 受入時の証拠 |
| --- | --- | --- |
| R1 原本・出力の保全 | 選択読込み、構造統合、Plan復元、既存レポート、Unitypackage出力を保持。原本を書き換えず、未知情報を再生成しない | 入力hash不変、固定Plan、出力manifest、Asset/metaのバイト比較 |
| R2 診断の独立性 | 診断の未実施・失敗・取消・上限超過でComposerの受付範囲や生成判定を変更しない | 各状態の独立JSON、生成操作・再実行の記録 |
| R3 識別子と意味の保全 | fileIDはsigned 64-bit十進文字列。GUIDは共通正規化。位置はUTF-16コード単位。未選択・未対応・曖昧を確定欠落に変換しない | 大きなfileID、日本語・絵文字、GUID大小文字、選択外参照の回帰 |
| R4 所有権と全件性 | poolの所有者とSDKの借用者を区別。原本bufferをdetachしない。全件JSONと全素材診断を区別 | 所有権表、取消・復帰・dispose、保存JSONの版・件数・対象一致 |
| R5 評価の正確さ | 解析成功、生成可能、出力保全、Unity動作を別判定。未測定値を推定で補わない | 工程別の生データ、未実施一覧、必須検証の証拠 |

新DSL、AAC本体のWASM移植、汎用IRへの全面移行、Create/Edit/Reset編集基盤、SIMD、常駐Workerを今回の必須範囲へ追加しない。Unity Editor・MA・VRChatでの動作保証も、今回のブラウザ側保全・軽量化とは別工程とする。

## 3. 現行実装から分かったこと

### 3.1 既に実装済みの内容

- 共有診断の独立状態、SDK呼出し前のoperationId、入力・選択・Planのrevision、旧成功・旧失敗・旧進捗の排除。
- 全入力を確認してからのコピー、原本bufferの保全、診断側上限とComposer受付範囲の分離。
- 50件単位の表示、全件JSONの遅延整形と再利用、確定結果の容量キャッシュ、GUID大小文字差分の修正。
- 生成物診断、明示的に保持した基準との比較、診断失敗後の再開。prepareの30秒deadlineとmessageerror処理。
- 依存不足・競合への移動、部分解析表示、Expression適用範囲の表示など、過去の使用感評価を受けた案内。

これらを新機能として再実装しない。小さいファイルの解析は既に最大8ファイル単位のバッチを利用しており、「常に1ファイルごとにWorker起動」とする旧評価も現行にはそのまま当てはまらない。

### 3.2 今回の静的照合で確認した改善候補

| ID | 確認できた構造 | まだ分からないこと |
| --- | --- | --- |
| G1 初期依存 | `app → diagnostics-panel → compute/client → pool → tasks` がstatic importで接続されている。poolは初回ensure時に生成され、診断開始のほか未実施JSONの表示・保存もその契機になる。pool生成だけでWASM実行が始まるわけではない | 初回表示への影響量、キャッシュ状態ごとの差 |
| G2 表示整形 | ページ表示のたびに最大50項目を個別にJSON整形。coverageも参照更新時に全文整形する | 実素材での表示時間。全レポート再生成は既に解消済み |
| G3 一時コピー | SDKの結果待ち後、照合に必要なのはpath集合と件数だが、呼出し側が入力payloadへの参照を保っている | GCの実解放時刻、ブラウザ全体のピーク削減量 |
| G4 取消と実終了 | prepareの取消・timeoutで画面の待機は終了する一方、Composer Worker側の処理終了確認は別に扱われていない | 次の操作に実害が出る条件。新しい製品不具合とは未認定 |

生成物を保持する `diagnosticOutput.assets` は、繰り返し出力診断するために使用されている。保持時に本文を再コピーする経路は確認されず、次の関連操作で破棄される。この保持を不要と判断して削除しない。比較基準の明示的保持も維持する。

| 項目 | 現状 | 解消方法 |
| --- | --- | --- |

## 4. 提案する改良項目と採用順

### ① 任意診断の重い依存を初回操作まで遅らせる【優先：高】

**変更案：** 既存のFile SDK遅延importを維持し、`diagnostics-panel.mjs` のcompute static importを外して、compute/poolの読込みも診断開始時まで遅らせる。軽いパネルと状態記録は起動時から使え、未実施JSONの保存にWASMやpoolを要求しない構造にする。ロードPromiseを再利用し、失敗後は再試行できるようにする。

operationId・revisionはロード開始前に確保する。import中の取消・入力変更・dispose後に届いた結果から、新しいpoolや診断を起動しない。poolはページ所有、SDKは借用という責任を保つ。

**受入案：** 診断未使用時に診断起因のcompute/Unity解析モジュール・WASM要求が発生しないことをネットワーク記録で確認する。他の既存機能が必要とする依存は一律禁止しない。初回診断、再診断、ロード失敗、ロード途中の取消から復帰できる。初期負担の減少と、初回診断へ移った負担を両方記録する。

**根拠：** G1、Tips08・16。読込み量削減は確認できる設計目標だが、速度改善量は実測後に判定する。

### ② 診断行を要約し、詳細JSONは開いた時に整形する【優先：高】

**変更案：** 各行に種類・対象パス・理由を短く示し、詳細を展開した時だけ個別JSONを整形する。coverageは件数・選択範囲・未解析の有無を通常表示し、全文は詳細欄に置く。同一結果の整形内容は再利用する。

検索・ページ送りと全件JSON保存を分離した現行契約は保つ。該当する既存欄を一意に特定できる場合に限り、選択・依存・Parameter欄へ移動できるようにする。曖昧な指摘を自動修正したり、診断が0件という理由だけで生成可能にしたりしない。

**受入案：** 50件表示、検索で1件に絞った状態、前後ページへの移動でも、未展開行や全レポートのJSON整形を繰り返さない。必要なエラーと次の操作は詳細欄を開かず読める。キーボードで詳細・移動先へ到達でき、状態通知も確認する。保存JSONは検索状態にかかわらず全件を含む。

**根拠：** G2、Tips08・16、過去使用感資料。既存のtaskGuideや復帰案内は活かし、画面全体を作り直さない。

### ③ 取消・失敗後の状態と復帰を工程ごとに明確にする【優先：高、まず影響確認】

**変更案：** 「表示を取消にした」「旧結果を無効化した」「準備処理が終了した」「SDKのjobが停止した」を区別して記録する。取消・timeout後に遅れて届くprepare結果を終端確認として扱う方法と、次のWorker要求の扱いを確認し、必要な箇所だけ修正する。

遅れたprepare結果から確認できるのは、対応するoperation/revisionの準備応答が届いたことまでである。Worker全体の停止、取消成功、SDK job終了、資源解放まで証明したとは扱わない。

同じWorkerがまだ使用中なら、生成条件そのものを否定せず、実行待ちと区別する。診断のためにComposer Workerを無断でterminateして読み込んだ状態を失わせない。復旧に再読込みが必要な場合は、保持できる選択・Planと再開箇所を明示する。既存の30秒上限は測定前に延ばさない。

**受入案：** prepare中・SDK実行中・比較基準保持中の取消、timeout、messageerror、dispose、直後の再実行を確認する。旧成功・失敗・進捗が現在の結果を上書きしない。別の利用者・処理が所有するpool/jobを破棄しない。診断失敗後にも、既存条件を満たす生成と保存済み成果の利用が保たれる。

**根拠：** G4、Tips04・16、ワークフローF09・F12。実害が確認されなければ、必要な状態の説明と証拠の明確化に留める。

### ④ SDKへ渡した一回用コピーの参照保持を短くする【優先：中】

**変更案：** payloadから照合用のpath集合・件数を先に取り出し、SDK呼出しとPromise待機を分離する。現在のSDKはPromiseを返す前に入力のsnapshotコピーを作るため、その契約を固定版で確認したうえで、一回用payloadへの呼出し側参照を外す。

同期例外、前側のコピー後に比較の後側で失敗する経路、非同期失敗、取消を分けて後始末する。原本・明示的な比較基準・生成物診断用の保持データは変更しない。共有SDKを差し替える場合は、同じsnapshot契約が成立するか再確認する。

**受入案：** 原本と比較基準のbytes/hashを保ち、連続比較・失敗後の再実行が成功する。SDK完了後の照合は小さいmanifestだけで成立する。保持参照の短縮とGCの実解放を区別し、測れなければ「ピークメモリ削減」とは評価しない。

**根拠：** G3、Tips04・08。上限付きの必要な保持まで削らない。

### ⑤ Module再利用・解析バッチを、残る負担に応じて調整する【優先：条件付き】

①〜④の評価後もstartup/compile/転送が支配的で、変更による利用者利益が見込める場合だけ比較する。現在の画面条件はWorker 2、moduleReuse=false、parseBatchSize=8を基準にする。

moduleReuseの比較では入力・Worker数・キャッシュ条件を揃え、compile呼出し数、Instance生成時間、全体時間、出力一致、失敗復帰を確認する。Module再利用と常駐Workerは別の案である。InstanceだけでなくMemory・Global・Table・ホスト状態の共有有無も点検する。

**採用案：** 一貫した改善が観測でき、機能・取消・利用者分離を損なわない場合に限り、既定値変更を具体的な差分として提示する。改善を示せなければ現行設定を維持して終了する。既存のバッチをさらに大きくすることや常駐化は、この結果なしに進めない。

## 5. モジュール構造の整理方針

| 責務 | 主な対象 | 今回の整理 |
| --- | --- | --- |
| 構成・生成判断 | `app.mjs`、task-guide、既存composition/generate | 既存の生成可否と導線を維持。診断の合否を混入させない |
| 表示 | `lib/diagnostics-panel.mjs` | 要約、ページ送り、詳細の遅延整形、全件保存 |
| 診断の状態・契約 | `lib/shared-diagnostics.mjs` | 操作ID、revision、外側JSON、計測、一回用payloadの寿命 |
| 素材の所有と受渡し | `worker.mjs` のdiagnostic-export | 全入力preflight、新規コピーの転送、生成物の必要な保持、終端確認 |
| 共有計算・Unity解析 | `shared/compute`、`shared/unity-analysis` | 既存APIと上限を利用。Composer側の調整で済む間は共通基盤を変更しない |

新しい共通モジュールは、少なくとも実在する複数の利用先と同じ契約を確認してから抽出する。まずComposer内の依存と所有権を明確にし、全ツールへの波及や別系統のランタイム作成を避ける。新規ファイルが必要でも、遅延ロードと後始末をまとめる小さな補助モジュール程度に留める。

## 6. 実装工程と計測計画

### 実施する順序

| 工程 | 作業・成果物 | 次へ進む条件 |
| --- | --- | --- |
| 1 基準を固定 | 最新main/Sites、既存契約、入力・選択・Plan・出力hashを照合。C01用の保存物を探す。計測条件と必要な回帰を固定 | 確定条件・提案・未確認を区別し、改良前の証拠を保存できる |
| 2 基準を計測 | 現行の最新PagesでC12の基準測定。容量計算区間の観測追加が必要なら、計測だけの変更を静的確認してPagesへ反映し、その最新版で測る | 比較に使う版・入力・測定区間・生データが確定 |
| 3 最小変更 | ①初期依存、②表示整形、③取消・復帰を順に扱う。④はコピー契約を確認して別差分にする。⑤は計測結果で要否を決める | 保全レビューと静的確認を通過。各変更を独立に戻せる |
| 4 公開後に照合 | Sites用ソースとPages投影を確認し、Pages更新成功後にその最新版をCodex/dotのクラウドへ取得。配信バイト、操作、全件JSON/packageの実ファイルを照合 | 対象版の必要な回帰・比較・回収が完了 |
| 5 受入・記録 | RESULT/VALIDATION/WORKLOGへ根拠と未完了を追記。採用・保留・棄却を確定 | 必須項目の証拠が揃う。C01/C12が残れば保全計画全体は未完了 |

**動的検証の順序はユーザー指定を優先する。** 一般ワークフローの実行・回収と公開の順番をそのまま当てはめず、本件では「静的確認 → Pages更新 → 最新版のクラウド実行」を守る。未公開候補や旧版生成器を実行しない。比較元Aは、それが最新Pagesである時点で測って保存し、改良版Bの公開後は保存済みAと最新Bを比較する。計測時にAを再実行しない。

公開前に行えるのは構文、依存、差分、hash、出力仕様の静的照合まで。公開済みであることと検証合格は分け、必須証拠が未取得の版を完成と呼ばない。配信経路に403等が出た場合は経路障害として記録し、製品不良へ読み替えない。

### 最小の比較設計

対象素材は、既存証拠にある通常素材と多件数素材の2組を基本にする。入力bytes/hash、選択、Plan、browser版、端末条件、Worker数、moduleReuse、parseBatchSizeを固定する。

コピー計測・入力投入・出力回収には既存経路を使い、採否判断に必要な最小限の観測だけを加える。計測基盤や回収harnessの新規開発を独立の目的にしない。

| 観測 | 区間・方法 | 採否に使う判断 |
| --- | --- | --- |
| 初期読込み | ページ要求からComposerの最初の操作が可能になるまで。依存要求・転送量も保存 | ①が未使用時の負担を減らし、初回診断へ過剰な待ち時間を移していないか |
| 一連の操作 | 読込み→同じ選択・Plan復元→入力診断を実行する/しない→生成完了。同条件で比較 | 診断の追加負担、改良前後の生成手順への影響 |
| 診断の内部区間 | prepare、SDK settlementまで、外側JSON容量計算、freeze/公開処理、画面更新、必要時の全文整形を区別 | 計算外のどこに時間が残るか。SDK totalMsだけで全体を説明しない |
| 表示・保存 | 検索、ページ送り、詳細展開、全件JSON整形、Blob作成・download開始を区別 | ②の効果、保存する情報の全件性 |
| メモリと保持 | 計測API・指標名・取得可否を記録。入力コピー量、保持量、WASM容量、heap/プロセス観測を混同しない | ④の保持短縮と実測メモリの関係。取得不能はnull/未測定 |

初期案は各素材・各経路を5回反復し、全値・中央値・最小最大を残す。改良前後2版×2素材×診断有無2経路×5回で40手順分。初回のページ読込み・初回診断は反復中の再実行と分け、測定時のキャッシュ条件を明示する。これは効果を判定するための提案数であり、失敗再試行の回数ではない。

入れ子の時間を合算しない。画面更新処理の終了と実際の描画完了も同一視しない。JSON容量の計測値をJSON自身へ追記して容量を再計算する循環を避け、独立した端末内計測記録に置くか、測定対象の定義を明示する。

性能の数値目標は未合意である。別製品の「10%」等を流用せず、基準計測のばらつきと利用者の待ち時間から、採用に必要な差と許容悪化幅を**変更後の結果を見る前に**固定する。差が判別できなければ速度改善を認定しない。ピークメモリの取得成功そのものを新たな必須条件にはしない。

⑤の追加比較が必要な場合は、支配的な負担が出た1素材・同一条件で再利用なし/ありを各5回までとする。新しい判断材料が得られなければ広範なベンチマークへ拡大しない。入力やログの外部収集は追加しない。

### 所要の目安

通常の取得・公開経路が利用できる場合、工程1〜2で半日〜1日、工程3で1〜2日、工程4〜5で半日〜1日が目安。合計2〜4作業日を仮置きする。C01保存物の取得待ちや配信障害は別扱いであり、完了日を保証する見積りではない。

## 7. 検証・失敗時の扱い

### 必要な回帰

| 群 | 内容 | 証拠の扱い |
| --- | --- | --- |
| 保全 | 同じ入力・選択・PlanのAsset/meta、原本不変、Plan復元、診断なしの生成 | 改良前保存物と照合。C01の旧基準との対応は別に残す |
| 非同期 | 同期/非同期例外、ロード中取消、prepare/SDK取消、旧通知、timeout、dispose、再開 | 表示終端、計算終端、資源解放を別に記録 |
| 型・範囲 | fileID文字列、UTF-16、日本語・絵文字、GUID大小文字、選択外・参照のみ・opaque・曖昧 | 意味の変更がないこと。診断上限超過でもComposerの受付を保つ |
| 表示・回収 | 多件数、ページ送り、絞込み、詳細、キーボード、全件JSON/packageの取得 | download開始だけを成功にせず、回収ファイルのbytes/hash・件数・対象版を確認 |
| 性能 | C12と各採用候補の前後比較 | 生データと境界を保存。未測定を0や合格にしない |

既存の17境界ケース、選択読込み12群、共有GUID/JSON8ケース等の証拠は、対象コード・契約・入力が変わらない範囲で再利用する。変更が影響するケースだけ再実施し、数字を増やすための全試験反復は行わない。

### 障害から再開する位置

| 状況 | 対応 | 再開点 |
| --- | --- | --- |
| 試験側の不足・誤設定 | 最初の失敗を保存し、製品不良と分離してharnessを修正 | 影響したケースのみ |
| 生成成功後の回収失敗 | 成功出力と保存状態を保全 | 回収・照合から。生成を繰り返さない |
| startup/経路障害 | 初回エラーと版を残す。後続成功だけで原因解決としない | 原因に対応する経路確認から |
| 取消・後始末の不明 | 所有者、operation/job、最終応答を確認 | 停止確認後。別処理の成功物を消さない |
| C01資料不足 | 保存物の所在と不足する対応情報を記録 | 該当比較だけ保留し、独立作業を継続 |

同一障害の再試行は、新しい根拠・変更点・期待結果がある時だけ行う。ワークフローの既定2回は上限であり、必ず2回試す意味ではない。担当やタスク名を変えて上限をリセットしない。

ロールバックは今回の差分のみを戻し、VR180等の並行更新を保持する。入力素材の品質や上限を下げて合格へ変更しない。
