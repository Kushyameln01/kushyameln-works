# 今回の作業は、通常の受け渡しを軽量化し、workflow由来の要求shapeとownerの実行能力で接続を判断する改修です。

##共通方針は次のとおりです。
- 通常入口は、既存descriptorの操作・使用モデル／対象・shape・dtype・軸・意味・正規化状態を使います。
- ownerは、要求に対する対応可否と理由を返します。
- 独立参照・誤差gate・詳細receipt・全中間出力保存は、診断側へ分離します。
- shape計算、数値演算、mappingの正本をそれぞれ一つにし、各モジュールの単独利用を維持します。

#管理担当へ：通常入口と共通shape導出を実装してください。
1. 既存の判定・queue・snapshotを再利用し、通常入口から独立数値参照、gate、事前PASS、数値receipt、全中間E4保存の必須条件を外してください。従来の診断入口は維持してください。
2. サンプルworkflow由来のshape計算を、共有する一つの正本として実装してください。以下を含めてください。
   - sourceの実frame数と、元のresize規則
   - 参照画像の長辺上限848、16pixel単位のPython互換丸め
   - latentの時間・空間圧縮
   - patch化、context順、token連結、source_id
3. 算出した要求をownerへ渡し、返された実行可能範囲で判断してください。管理独自の固定Profile一覧を通過条件にせず、非対応の場合はownerの理由を返してください。
4. ロード済み実体の確認と、構成変更時の失効を内部化してください。通常のデータ受け渡しに、利用者がsource・build・kernel証跡を添付する方式を要求しないでください。取消・古い結果の不採用・解放は維持してください。
完了条件： 対応shapeは参照配列なしで通常実行でき、非対応shapeは具体的理由で停止すること。workflowの式に合うことだけで、実行可能と判定しないでください。


#各担当とも、変更検証では既存の数値参照を利用し、通常入口の出力が既存の診断基準を満たすことを確認してください。今回の完了範囲は、既知の対応shapeでの通常実行・非対応判定・取消・解放までです。
