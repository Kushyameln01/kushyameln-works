# Diffusion Profile宣言と証拠の対応

`p0-bindings.json` はDiffusion ownerの外側sidecarである。Profile・管理照合規範・数値規則は文書版 `1.0-draft.1`、固定commit `6dae9a6fac3e9ad29ea941f22211edbe4aa894ad` の原本に結ぶ。native API、tensor、requestへrecordId/normIdを追加する契約ではない。管理の `evaluateEdge` や数値式を別実装せず、既存のsourceと数値証拠へたどるための情報を提供する。

対象は4つの数値実行record、3つのmean正規化record、未実装のgenerated復元依存である。関連する12normのnative field pathと、管理・LoRA・VAEへの外部依存を記録する。`integrity.mjs` はこのsidecarと実際に渡したcode/kernel/reference bytesの整合を検査する任意の独立ES入口で、native Workerを起動したり管理の判定状態を変更したりしない。

## sourceと採用の区別

既存証拠のsourceは `5f880fd8eef9e63054bdbf772bc9a525ef3a3bf3`、native buildは `diffusion-models/0.1+35b5ecdf924b13ccfcd08ec1eeaf840700dfc7c69acd168bbb39e72376542a20`。52sourceの閉包と、kernel、oracle、既存receiptを含む71assetの完全commit/path・bytes/SHA-256を持つ。

各 `reusedProfiles[].validation` の `freshRun` はfalseであり、記録済みの数値結果を保持する。今回のP0検証はファイル実体と宣言の照合で、新たなモデル推論ではない。管理が採用したDiffusion438とowner5fも別組合せのままである。

新しいsource/buildを固定した後は、generatorの `--candidate-commit <完全SHA>` で `candidateBuild` を別欄へ記録できる。ここでbaselineの数値receiptのcommit/buildを変更しない。候補codeの取得成功だけでは `numericAcceptance=NOT_VERIFIED` を解除しない。変更境界のP2/P4数値証拠と、管理の採用記録は別途必要となる。

F5の原本は `1317758bbba2b13603752d8c910ae2c6e77f78c5`。`latent-space/test-cases.mjs`（6016 B、SHA `82811c79dba38dd809a5e9d5f3d6c58bdfa17a87f2a928f2aa6303596a2f843b`）の独立oracleと、同commitのREADME・`development/diffusion-models/rev3-latent-space.json` が比較前2e-6を記録する。F1/Rectから転用した数値ではない。原commitは公開902/f522 sourceの祖先にある。

このF5 gateはVAEの実F5 encode/decode精度を認定しない。原本は事前固定と明記するが、最初の実行以前の独立した時刻認証まではない。固定catalog側の `NOT_VERIFIED_FOR_F5_IN_THIS_CATALOG` は無改変で保持し、ownerが新たに取得した出典をsupplementとして分離した。元WASM `ffd1c821…` のreceiptと、5fの新WASM `bd42d4…` によるF5回帰receiptも別に追跡する。

gate/receiptだけが不足する場合、契約上のCOMPATIBLEをUNVERIFIEDへ変更せず、数値受入NOT_VERIFIED・準備BLOCKEDとして区別する。P0 sidecarの整合検査成功自体は、その管理判定や生成READYを返すものではない。

## ownerとmetadata

LoRA full-shape/slice・両registry・sink/consumer取引のmapping正本はLoRA `createDiffusionDiagnosticAdapter` / `lora-diffusion-diagnostic-adapter/0.1`。5fのDiffusion `lora/v2-adapter.mjs` は歴史的な回帰経路として記録し、現在の正本adapterへ重ねない。Diffusionは不変base復号、native registry/provider/sink/consumerを所有し、LoRA積やloader数式を複製しない。

native mean transformは既知のcontext fieldを所有コピーし、frame配列の順序と重複を保つ。未知context keyは現在拒否し、返tensorも既知fieldで構成する。管理・codecは任意metadataを外側sidecarへ保持し、nativeに未定義fieldを強制しない。`N-ARTIFACT` の任意metadata保全を、nativeが任意fieldをそのまま返す能力と混同しない。

公開pointwise1,048,576、内部scheduler4,194,304、Text conditioning2,097,152、本番latent2,096,640は別のoperation予算である。上限の相互転用、host値だけの引上げ、meanとgeneratedの改名を許可しない。

## 整合検査の呼出し

```js
import {verifyDiffusionOwnerBindings} from './integrity.mjs';
const receipt = await verifyDiffusionOwnerBindings({
  declarationBytes, // Uint8Array
  expectedSha256,   // 固定Git/受領receiptから得た信頼するsidecar digest
  referenceFiles,   // Map<canonical repository path, Uint8Array>
  ownerFiles        // Map<`${commit}:${path}`, Uint8Array>
});
```

expectedSha256を同じ未確認入力から計算して信頼根拠にしない。各Mapのbytesは最初のawait前にsnapshotする。code/kernel bytesは`assets`の長さ/hash、参照JSONは固定catalogの長さ/hash/版、profileはrecordのnative IDと全軸shape/meaning/exportへ照合する。hash照合済build-infoのBUILD_ID/BUILD_SOURCE_SHA256/BUILD_SOURCESをevalせず取得し、実source閉包の全件とdigestへ結ぶ。baselineと候補の宣言同士が一致するだけでは通さない。戻る `verified:true` はこの整合scopeだけを表し、モデルsession・signature認証・数値再実行の証拠ではない。

## 再現

```sh
git fetch --no-tags origin 6dae9a6fac3e9ad29ea941f22211edbe4aa894ad
git fetch --no-tags origin codex/diffusion-api-adjustment
python tools/diffusion-models/build-p0-bindings.py
python tools/diffusion-models/test-p0-bindings.py
# 新code commitを候補欄へ記録する場合だけ指定する
python tools/diffusion-models/build-p0-bindings.py --candidate-commit <完全SHA>
python tools/diffusion-models/test-p0-bindings.py
```

Python検証入口は必要な固定Git code bytesを一時directoryへ受領し、Node12caseへ渡す。原本model/LoRA payloadの読出し、巨大再hash、ネットワーク取得、モデル推論を含めない。正本JSONのコピー・hash receiptは `development/ai-connection/profile-adoption/received-reference/` と `p0-acquisition.json`、証拠indexは `p0-evidence-index.json`、検証記録は `p0-verification.json`。
